# DOCX 翻译独立后台路径计划

## 一、评审结论

整体方案方向正确：DOCX 不应复用 PDF 的版面重建逻辑，也不应再以“整段翻译后按字符比例切分”的方式恢复格式。当前实现已经证明，在限定的 OOXML 范围内，只修改既有 `w:t` 可以保留 run 属性、超链接关系和内联非文本节点。

本轮评审事项状态：

1. **P0，已完成：输出文件通过同目录临时文件保存并原子替换。** 模型失败、取消或保存失败时不会发布半成品，临时文件会在 `finally` 中清理。
2. **P0，已完成：增加 worker 入口级验证。** 已覆盖任务状态、数据库记录、输出文件登记失败、预览失败降级和取消后的清理。
3. **P0，已完成：把支持的 OOXML 结构写成明确契约。** 当前只处理段落的直接 `w:r` 以及直接 `w:hyperlink/w:r`；修订标记、内容控件等容器内文本会被跳过。
4. **P1，待人工验收：使用真实样本文档做兼容性验证。** 至少用 Microsoft Word 和 LibreOffice 各打开、另存一次，检查修复提示、链接、图片、域和布局是否正常。
5. **P1，基础能力已完成：记录可观测指标。** 成功日志包含段落数、片段数、零片段文档、保存耗时和总耗时；失败阶段可结合任务状态及异常日志定位。线上指标聚合仍属于发布后工作。

## 二、背景、目标与成功标准

原 DOCX 分支与 PDF 共用任务状态机，其中 DOCX 文本替换会删除段落中的全部 `w:r` 和 `w:hyperlink`，导致字符样式、超链接和其他内联内容丢失。

本次目标：

1. 将 DOCX 翻译放入独立模块，同时复用上传、队列、任务状态、存储、预览和下载链路。
2. 保持受支持范围内的 OOXML 节点顺序、run 属性、超链接关系以及内联非文本内容。
3. 对不同格式或不同链接归属的文本分别翻译，不根据译文字符数猜测格式归属。
4. 明确失败、取消和无可翻译文本时的行为，确保任务状态与磁盘结果一致。

成功标准：

- 输出仍是可正常打开的 `.docx`，且 Word/LibreOffice 不提示修复。
- 除 `w:t` 文本值和必要的 `xml:space` 外，受测段落的结构、关系和格式签名保持不变。
- 翻译片段与模型结果严格一一对应；数量不一致时任务失败，不写入最终文件。
- 取消或异常后没有输出记录，也没有最终路径文件或遗留临时文件。
- PDF 路径及其任务行为不受影响。

## 三、范围

### 3.1 本期支持

- 扩展名为 `.docx` 的 Office Open XML 文档。
- 主文档正文中的顶层段落。
- 主文档顶层表格的单元格段落；合并单元格按底层段落元素去重。
- 段落下直接出现的 `w:r/w:t`。
- 段落下直接出现的 `w:hyperlink`，以及其中直接出现的 `w:r/w:t`。
- 与文本相邻或位于同一 run 中的 drawing、tab、手工换行和域节点的结构保留。

### 3.2 明确不支持

- `.doc`、`.docm` 及其他非 `.docx` 格式。
- 页眉页脚、脚注/尾注、批注、文本框、嵌套表格。
- 修订标记（如 `w:ins`、`w:del`）、内容控件 `w:sdt`、`w:smartTag`、`w:customXml`、`mc:AlternateContent` 等包装容器内的文本。
- 图表、SmartArt、公式、嵌入对象内部的文本。
- 动态域结果的长期一致性；Word 重新计算域后可能覆盖已翻译的显示值。
- DOCX 预览编辑回写。现有预览只展示有限正文文本，本期仅保证不回归，不扩展为完整 DOCX 渲染器。

对于不支持的结构，本期原则是**保留原节点但不翻译其内部文本**，不得展开、删除或重建这些节点。后续扩展应逐类增加遍历规则和回归样例。

## 四、设计方案

### 4.1 模块边界

```text
run_translation_job (translation.py)
  ├── .pdf  -> 现有 BabelDOC 路径
  └── .docx -> translate_docx (docx_translator.py)
                 ├── python-docx + 标准库
                 └── 调用方注入翻译器、批量翻译函数、进度和取消回调
```

`docx_translator.py` 不在运行时导入 `translation.py`，不读取数据库、运行时配置或任务模型，也不自行创建翻译器。任务编排和状态迁移继续由 `run_translation_job` 负责。

当前入口为：

```python
def translate_docx(
    input_path: str,
    output_path: Path,
    *,
    translator: OpenAICompatibleTranslator,
    translate_segments: Callable[..., list[str]],
    source_language: str,
    target_language: str,
    on_progress: Callable[[int, int], None],
    cancel_check: Callable[[], None],
    on_rebuilding: Callable[[], None],
) -> int | None:
```

`OpenAICompatibleTranslator` 仅在 `TYPE_CHECKING` 下引用，所以当前没有运行时循环导入。若继续强化模块独立性，可将 `translator` 视为传给 `translate_segments` 的不透明对象；无需为此新增只有一个实现的接口层。

### 4.2 收集顺序与去重

按文档顺序收集正文段落，再按表格、行、单元格顺序收集顶层表格段落。`python-docx` 可能从合并单元格的多个网格位置返回同一个段落，因此用段落 XML 元素身份去重。

只有至少包含一个非空白、受支持 `w:t` 片段的段落进入翻译列表。若整个文档没有可翻译片段，应跳过模型调用，仍生成结构等同的输出文件，并在日志中记录 `spans=0`。

### 4.3 连续格式片段

按段落 XML 实际顺序扫描受支持的普通 run 和超链接 run：

1. `w:t` 是文本单元。
2. 相邻、`w:rPr` XML 完全相同且属于同一超链接容器的文本单元合并为一个片段。
3. 超链接边界、格式变化，以及 tab、换行、drawing、域等非文本节点会结束当前片段。
4. 片段首尾空白不发送给模型，由写回逻辑原样补回。
5. 显式属性不同的 run 即使视觉效果相同也不合并，以结构正确性优先。

必须保持以下不变量：

- 片段顺序等于 OOXML 中的可见文本顺序。
- 片段不会跨超链接、格式或非文本节点边界。
- 普通文本和超链接文本不会互换容器。
- 不使用字符比例切分译文。

该策略会让混合格式段落产生多个翻译片段，句子级上下文可能变弱，这是本期为确定性格式归属接受的权衡。

### 4.4 翻译与写回

先收集全部片段并完成全部翻译，再修改内存中的文档。翻译结果必须与片段数量严格一致；任何模型异常、取消或数量不一致都应在保存前失败。

写回时仅修改现有 `w:t` 的文本值，不使用 `Run.text` setter，也不删除或重建 `w:r`：

- 译文写入片段的第一个 `w:t`，其余 `w:t` 置空。
- 原 run、超链接、关系、drawing、tab、换行和域节点保留。
- 根据新文本首尾是否为空白同步设置或移除 `xml:space="preserve"`。

将译文集中到第一个 `w:t` 不会改变本期片段的格式归属，因为同一片段内的 run 具有完全相同的显式 `w:rPr`。它会改变文本在等格式 run 之间的分布，因此验收比较的是节点/格式/关系及可见文本，不要求每个 run 保持原字符数。

### 4.5 保存、失败与清理

最终文件不能直接写入结果路径。保存流程应为：

1. 在最终结果文件同目录创建唯一临时文件。
2. `document.save(temp_path)`。
3. 重新打开临时文件做最小完整性检查，并确认它是合法 DOCX 包。
4. 再次执行取消检查。
5. 使用 `Path.replace` 原子替换到最终路径。
6. 在 `finally` 中清理临时文件。

若翻译、保存、校验、取消或后续输出登记失败，任务沿用现有失败/取消状态机；不得创建 `JobFile.OUTPUT` 记录。若最终文件已经落盘但数据库登记失败，任务编排层也必须删除该孤儿文件。

### 4.6 进度与取消

DOCX 状态约定：

| 阶段 | 状态 | 进度 |
|------|------|------|
| 打开并收集 | `PARSING` | 5% 起 |
| 翻译片段 | `TRANSLATING` | 20%–80% |
| 校验并保存 | `REBUILDING` | 88% |
| 输出登记与预览 | 沿用现有任务编排 | 88%–100% |
| 完成 | `COMPLETED` | 100% |

每个片段翻译前执行取消检查；全部翻译后、保存前以及原子替换前再次检查。保存单个 ZIP 包期间不承诺即时中断，但取消后不得发布最终结果。

## 九、剩余风险与后续方向

- **上下文质量：** 混合格式片段分别翻译会削弱句子级上下文。若真实样本对此敏感，后续采用模型可校验的内联标记协议，并为标记缺失、重复或重排设置明确失败策略；不能恢复字符比例切分。
- **调用数量：** 显式 `w:rPr` 细微差异会增加片段数和模型调用。上线后依据片段数分布决定是否做“语义等价格式”归一化，不能仅凭视觉猜测合并链接或格式边界。
- **不支持结构：** 修订、内容控件和文本框中的文本会保持原文。扩展时按结构逐项实现和验收，不使用无边界的递归抓取全部 `w:t`。
- **资源消耗：** 上传限制约束的是压缩包大小，不直接约束 DOCX 解压后的 XML 和媒体体积。若线上出现超大或恶意文档，再在上传/解析边界增加压缩包条目数、解压总量和片段数上限。
- **动态内容：** Word 重新计算域、链接或嵌入对象时可能改变显示结果；本模块只承诺保存时的 OOXML 结构不被破坏。
